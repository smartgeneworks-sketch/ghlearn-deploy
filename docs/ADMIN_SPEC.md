# Admin Panel specification (user's request, condensed faithfully, section numbers preserved)

1. Goal: complete, professional, secure, fully functional admin panel for the AI learning platform (Ghana SHS curriculum). Centralized control over users, schools, subjects, curriculum docs, learner manuals, AI content, publishing approvals, assessments, games, analytics, AI config, system settings. No static dashboard or non-functional buttons; every action hits a backend API and persists. Inspect and reuse existing code; don't rebuild working parts.
2. Stack: existing (React/Vite/TS, Tailwind, TanStack Query, React Router, RHF+Zod, Node/TS/Express, Mongo/Mongoose, modular AI layer for LLM/doc processing/embeddings/illustrations, a React-compatible chart lib, Lucide icons, existing auth). No separate auth system and no duplicate models.
3. Design. A) Sidebar, permission-filtered: 1 Overview, 2 Schools and Institutions, 3 Users and Permissions, 4 Academic Structure, 5 Curriculum Management, 6 Learner Manuals, 7 AI Content Generation, 8 Content Review and Publishing, 9 Question Bank and Assessments, 10 Educational Games, 11 Classes and Enrolments, 12 Learning Analytics, 13 AI Usage and Costs, 14 Notifications, 15 Audit Logs, 16 System Settings. B) Top bar: sidebar toggle, global search, notifications, current academic year, admin profile menu, account settings, secure logout. C) Workspace: page title and description, breadcrumbs, action buttons, filters and search, paginated tables, forms and confirm dialogs, loading/success/empty/error states. Responsive on desktop/tablet/mobile. No excessive gradients, clutter, oversized cards or decorative charts.
4. Server-enforced RBAC plus permissions (e.g. review without publish). Super Admin: manage school admins, global curriculum, AI providers/integrations, platform usage limits, system-wide analytics and audit, global settings. School Admin: only their institution's students, teachers, classes, enrolments, subject assignments, school settings and school analytics; no access to other schools. Curriculum Admin: curriculum versions, subjects/strands/indicators, learner manuals, processing jobs, mappings, generation requests. Content Reviewer: review notes, illustrations and exercises; edit or request revisions; approve/reject; publish only if authorized. System Operator: service health, queues, permitted operational logs, retry failed jobs, investigate errors. Never rely on menu visibility.
5. Overview, all live data. Cards: students, teachers, schools, active users, subjects, uploaded manuals, published resources, pending reviews, failed processing jobs, AI requests and estimated cost. Charts: registrations over time, active users over time, subject enrolment distribution, manual processing status, generated vs published lessons, review workload, exercise completion trends, AI usage/cost, performance by subject (where authorized and real). Filters: date range, level, school, subject. Activity: recent manuals, recent generated content, pending approvals, failed jobs, recent admin actions, system warnings. Clicking a card or item opens the filtered management page.
6. Schools: add, edit, activate/suspend/archive, assign school admins, configure levels, programmes (learning areas) and subject combinations, school-specific permissions, student/teacher counts, school usage and learning analytics. Fields: name, unique identifier (validated), region and district, institution type, contact, levels, status. School-scoped auth.
7. Users: searchable, filterable tables for super admins, school admins, curriculum admins, reviewers, teachers and students. Create authorized user, edit permitted fields, assign/change roles, school membership, classes/subjects, activate/deactivate, secure account recovery, revoke sessions, created date and last login, audit history. Students show level, class, programme (Learning Area), subjects, status and an activity summary. Teachers show school, classes, subjects and status. Use invitation and recovery flows; never show passwords, hashes, keys or secrets. No self-escalation via unvalidated requests.
8. Academic structure: levels, academic years, classes/grades, programmes/pathways, subjects, subject categories, combinations (per programme and class, not one universal set), curriculum versions, strands, sub-strands, indicators/outcomes, topics/subtopics. Create, edit, reorder, deactivate, archive. Keep relationships valid. Block deleting elements referenced by active resources; prefer archive/versioning.
9. Manual library: upload PDF, DOCX, TXT, CSV and scanned PDF (OCR). Drag and drop, size and type validation, upload progress, processing status, duplicate detection, retry. Metadata: title, subject, level, programme, class, curriculum version, source/publisher, year, language, document version, licensing status, uploader, upload date, processing status, approval status, tags. Actions: details, preview original, download if permitted, update metadata, reprocess, inspect extraction, page-level text and figures, errors, archive, upload a replacement version (preserve previous versions and their links to generated resources). No auto-publish and no assumption that uploads are official.
10. Processing monitor: job id, manual title, subject, uploader, stage, progress if available, start/end timestamps, pages processed, OCR status, extraction status, indexing status, error summary, retry count. Statuses: Queued, Extracting, OCR processing, Mapping curriculum, Indexing, Awaiting validation, Completed, Failed. Inspect and safely retry failed jobs; no duplicate passages or embeddings. No fake progress; use real stage or an indeterminate indicator.
11. AI generation workspace from approved sources. Options: level, programme, subject, curriculum version, strand/sub-strand, indicator, topic/subtopic, source manual, section/page range, duration, reading level, depth, number of activities and questions, difficulty distribution, illustration requirements, language. Types: learner notes, summaries, worked examples, labelled diagrams, concept maps, infographics, real-life scenarios, individual/group/practical activities, research/project tasks, formative questions, revision cards, vocabulary, games, teacher prep. Pedagogy: outcomes, prior knowledge, inquiry, participation, collaboration, critical thinking, problem solving, real life, practicals, formative assessment, feedback/reflection, remedial/extension. Preserve source accuracy; never invent official indicators. Controls: generate a resource, generate a full lesson, regenerate a section, edit, preview/regenerate illustration, compare versions, save draft, submit for review, cancel/retry. Background jobs; show real provider errors, usage estimates and states.
12. Review queue: title, subject, topic, source manual, generation date, creator, curriculum mapping, status, assigned reviewer, revision history. Statuses: Draft, Generating, Awaiting review, Changes requested, Resubmitted, Approved, Published, Archived. Actions: open, compare with source, source references, edit if authorized, inspect illustrations, check Q&A accuracy and alignment, comments, request revision, approve, publish if permitted, archive. Confirm publish/archive. Record who and when. Block publishing while mandatory review is incomplete. Published content visible only to eligible students/teachers by subject, class, programme and institution.
13. Question bank: manual create, generate from approved manuals, edit, review answer keys, rubrics, subject/topic, objectives, difficulty and marks, time limits, preview as student, approve/archive, assemble assessments from approved questions. Types: MCQ, true/false, short answer, fill-in-the-gap, matching, ordering, structured, essay and others. Track versions and usage. Verification workflow for generated answers.
14. Games: quiz, matching, flashcards, vocabulary puzzles, sequencing, diagram labelling, classification, timed revision, scenarios. Each linked to subject, topic and objective. Create manually, generate from approved content, preview, edit, difficulty, scoring and hints, approve/publish, archive, participation and performance. Never publish unverified answers or broken interactions.
15. Classes: create/manage, assign teachers, enrol students, CSV import with validated template (column validation, duplicate detection, preview, error report, safe rollback/correction), review subject selections, configure permitted combinations, transfer students, academic-year changes, export enrolment reports. Never silently overwrite. Access only per confirmed enrolment and policy.
16. Analytics: enrolment, subject selection, active users, lesson completion, exercise completion, assessment results, topic performance, misconceptions, objectives needing remediation, game participation, tutor usage, content quality/review status. Filters: school, academic year, class, level, programme, subject, topic, date range. Charts, cards, searchable tables, CSV/Excel export by permission. Distinguish measured data from estimates or AI recommendations. Privacy-conscious; student-level data only for authorized users.
17. AI config: LLM, embeddings, OCR, illustration, vector search, object storage. Configure provider, model ids, per-user limits, school budgets, request limits, max input/output, retry, timeouts, allowed features, health checks. Secrets in env or a secret manager, never returned in full. If credentials are updated via UI: authorization, validation, audit. Show requests by provider, tokens/units, estimated costs, usage by feature and by school, failed requests, rate-limit events, budget thresholds. Label costs as estimates. A failed health check never shows as success.
18. Notifications: system and school announcements, publication notifications, processing-failure alerts, review reminders, account/security alerts. Audience and publication period. In-app, plus email if configured. No personal student info in broad announcements. Record delivery status.
19. Append-only audit: login and failed login, role/permission changes, activation/suspension, manual uploads/replacements, curriculum changes, approvals/publication, AI config changes, exports, deletion/archival. Record actor, action, resource type and id, timestamp, outcome, non-sensitive metadata. Restricted access. Never log passwords, tokens, keys or unnecessary student data. Prevent modifying/deleting history.
20. Settings: branding, app name and logo, theme, academic year, levels, default review policy, AI defaults, upload limits, allowed formats, notification settings, data retention, session settings, offline-download policy, feature availability, maintenance mode, terms and privacy notices. Validation and confirm dialogs for high-impact settings. Secrets stay out of the settings DB.
21. Backend: real endpoints and Mongo persistence; reuse and extend models (schools, users/roles, permissions, classes, academic years, programmes, subjects, subject enrolments, curriculum versions/elements, manuals, processing jobs, source passages, generated resources, content versions, review records, questions, assessments, games, AI usage, notifications, audit logs, settings). Indexes, validation, pagination, relationships, resource-level auth and school isolation. Documented, consistent REST. TanStack invalidation. Transactions or safe multi-step operations.
22. Performance: server pagination, search/filter, debounced search, lazy pages, efficient queries, caching, background jobs, only safe optimistic updates, skeletons, retry/recovery, clear errors, keyboard accessibility. Never load thousands of rows at once. No hard-coded stats or fake activity.
23. Tests for: admin auth, RBAC, school isolation, manual upload/management, curriculum CRUD, AI job handling, review workflow, publishing restrictions, question bank, game publishing, CSV import validation, analytics authorization, secret protection, audit creation, settings validation. Frontend plus backend API authorization; refuse direct API calls from unauthorized users.
24. Phases: 1 inspect; 2 admin routing, layout, nav, auth, permissions; 3 dashboard and activity; 4 users, schools, classes, subjects, academic structure; 5 curriculum and manuals; 6 processing monitor; 7 AI generation and review; 8 question bank, assessments, games; 9 analytics, AI usage, notifications, audit; 10 settings, security tests, responsive polish, deploy docs. Report after each phase: completed, tests run, issues, remaining work.
25. Definition of done: authorized admin signs in to permitted features; real dashboard data; schools/users/subjects/structure managed; manuals uploaded, processed, inspected, versioned; AI content created, edited, reviewed, published; backend enforces review/publish; questions and games managed; enrolment and subject access controlled; analytics from persisted records; AI usage and errors accurate; admin actions audited; secrets protected; responsive and accessible; automated tests on critical workflows and permissions; every control works; setup and deploy docs complete.
26. Final report: features, files/modules, DB changes, endpoints, tests and results, env vars, limitations, run/deploy instructions. Flag integrations that need credentials or paid services.
